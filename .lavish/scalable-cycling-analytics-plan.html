Dofek capacity plan

Make cycling analytics scale beyond one fast user

The target is not “run the same 20 statements faster.” It is a bounded cold-load path: two critical serving queries, one progressive activity query, shared caching, and compute sized from measured peak demand.

Recommended direction: reduce the cold cycling page to ≤3 ClickHouse statements, then give ClickHouse four dedicated CPUs and enforce a server-owned global query budget.

Implementation sequence

Each phase has a measurable exit gate; no concurrency or cache change ships on intuition alone.

1

Establish the capacity contract

Measure first
  • Define cold and warm SLOs: first useful chart, complete page, queue wait, and error rate.
  • Replay the cycling load at concurrency 1, 2, 4, 8, and during a dbt build.
  • Record actual CPU-seconds per serving statement and host CPU headroom.
2

Bound the page to three statements

Largest leverage
  • Add daily_cycling and cycling_activity incremental serving grains only for metrics currently requested.
  • Combine recent + season power curves into one parameterized query over the existing power-curve model.
  • Expose shared server contracts for cycling.performance and cycling.activities; clients only render returned values.
3

Control admission centrally

Protect latency
  • Replace the two independent two-slot queues with one global, work-conserving scheduler.
  • Classify procedures centrally as critical, secondary, or background so repositories cannot forget priority.
  • Use one total ClickHouse concurrency budget and observe queue depth/wait by class.
4

Correct compute and cache behavior

Scale safely
  • Allocate four ClickHouse CPUs only after confirming host headroom; otherwise move it to dedicated compute.
  • Keep the existing user-scoped Redis response cache and add cross-replica single-flight for identical cold misses.
  • Give dbt a constrained background profile so refreshes cannot consume interactive capacity.

What to ship

Capacity alone is faster; bounded work is what scales.

CPU only

Tactical

Raise ClickHouse from one to four CPUs and keep the ≈20-statement page.

  • Fastest immediate relief
  • Still expensive per cold user
  • Duplicate misses and dbt contention remain
Cost: capacity spend grows almost directly with user traffic.

Query reduction only

Efficient

Build the bounded serving path but leave ClickHouse on one CPU.

  • Much lower work per user
  • Likely acceptable at low concurrency
  • Little burst or refresh headroom
Cost: good economics, but one core remains a fragile ceiling.

Bounded path + 4 CPUs

Robust

Reduce to ≤3 statements, centralize scheduling, suppress stampedes, then add compute.

  • Approximately 6–10× more cold page capacity than today
  • Predictable latency under mixed workloads
  • Clear path to a dedicated node or replicas
Cost: more implementation work now; substantially better cost per user later.

Definition of done

The redesign is complete only when the cold path—not just the cache-hit path—passes.

✓

Query count

At most three ClickHouse statements for a cold cycling page, asserted in an executable integration/performance test.

✓

Latency

Critical content p95 <2 seconds and complete page p95 <3 seconds at the agreed concurrent load.

✓

Fairness

Interactive queue-wait p95 <250 ms while dbt runs; background work still makes progress.

✓

Parity and correctness

Web and mobile consume the same server-computed metrics, with old/new response parity tested against real ClickHouse fixtures.

✓

Cache stampede

Concurrent identical cold misses across both web replicas produce one backend computation per cache key.

✓

Scale model

Capacity sheet uses measured miss rate and peak page-load rate; alert before projected demand reaches 70% sustained capacity.
