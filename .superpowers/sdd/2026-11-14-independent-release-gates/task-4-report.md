# Task 4 — Protect publication order and recovery

## Scope and result

Implemented Task 4 on top of `83aec8780bdc45c415de8d224776d2c508c9a916` (base `83aec8780`). Changes cover the existing TestFlight publisher, OTA publisher, and server web release workflow. No release controller, generic CLI, repository settings, branch, or new workflow framework was introduced. Existing TestFlight public functions and command signatures remain available.

The target intent is now recorded before target mutation. Server intent/admission is in the parent `deploy-web-environment.yml`, so it runs before optional Terraform and the stack update; one per-host parent lock spans intent, Terraform/stack, verification, and receipt finalization, with no nested lock in the reusable stack workflow. OTA and TestFlight keep their existing per-target serialization. In-progress publication is not canceled by a newer run.

Server admission reads complete deployment history and authoritative latest statuses, verifies the deployment ref and payload identity, checks live web/worker source and immutable image identity, and compares candidate ancestry. Matching unresolved server intent remains blocked; it cannot be finalized from task identity alone. A separate finalizer runs only after the complete reusable stack workflow succeeds, re-runs the live web/worker image verifier, checks task labels and deployment identity, then finalizes the same receipt. The admitted digest reference is handed to the mutation workflow, preventing a second mutable-tag resolution. A candidate-only resolver mode inspects/pulls the candidate locally and explicitly clears `DOCKER_HOST`; it does not call Docker service inspection. Because the published manifest is arm64-only, this preflight pull explicitly selects `linux/arm64` and does not execute the image. The ordinary stack resolver keeps its existing remote service checks and migration-aware image safeguards.

OTA checks all pages of target history and blocks on unresolved attempts across runtimes. It uses the newest success for the requested runtime to verify/no-op that runtime's live UUID, and the globally newest success for forward-only source ancestry. Same source/identity is a no-op; an older source is superseded; unrelated history fails closed. OTA intent/recovery uses the same update UUID/runtime and verifies live signed update metadata. Recovery exports set the same Sentry release and request external source maps, then run the existing published-OTA verifier and upload maps from that export. GitHub status descriptions stay under the API's 140-character limit; source, digest, runtime, and update identity remain in the deployment payload. Server and OTA require the deployment ref to equal payload source SHA.

TestFlight reads paginated history through the end, rejects unresolved publication attempts, compares ancestry, and returns a narrow `upload` / `unchanged` / `superseded` decision for the production workflow. Existing exported functions and CLI commands are preserved. The upload intent is created before upload and only that receipt is finalized after native upload succeeds; upload completion remains distinct from later Apple processing availability.

Bootstrap remains fail-closed when target history is empty but a live target exists. The server path can derive immutable image/source identity from read-only live task metadata and asks an operator to establish the initial receipt if the source cannot be proven as a Git commit. OTA has no existing historical receipt; it requires a signed live UUID/runtime plus verified source SHA and prints exact GitHub deployment initialization instructions. Neither workflow treats empty history or a completed workflow as proof of a safe baseline. No live publication or failure injection was performed. The Expo recovery export was validated against installed CLI/EOAS options and controlled fixtures; a real production OTA artifact was not generated, intentionally.

## Review findings resolved

The lead's seven findings were addressed: (1) server recovery cannot auto-finalize an unresolved intent and finalization follows all reusable deploy verification; (2) OTA history is runtime-aware while preserving global ancestry and unresolved-attempt blocking; (3) status descriptions are bounded and fixture-rejected above 140 characters; (4) parent preflight has `setup-node-pnpm` and candidate-only ARM64 local inspection while live identity is read-only; (5) OTA recovery export includes the publication release value and external source maps; (6) GitHub deployment ref must match payload source; and (7) the admitted immutable image digest is passed through to stack mutation.

The controlled workflow tests execute extracted shell steps with fake `gh`, SSH, Docker, and live-verifier fixtures. They cover pagination, unresolved attempts, same identity, older/superseded and divergent candidates, mismatched ref/payload, OTA cross-runtime history, live-before-finalization failure and retry/recovery, short status descriptions, and immutable image handoff. Resolver boundary tests confirm the candidate pull requests `linux/arm64`, clears remote Docker selection, and makes no service calls; the standard resolver path remains covered.

## Source, lock, and recovery review

Reviewed all callers of the reusable server release path and moved admission into its parent so Terraform cannot precede it. The same target lock spans parent admission through the final receipt job; the child reusable workflow has no same-group lock, avoiding nested deadlock. The server web/worker release remains a single `docker stack deploy` with the same image. Existing source label, immutable digest, migration, and post-deploy checks are preserved. TestFlight continues to use its existing lock and upload path. OTA keeps its production target lock and deploy signature/asset verifier. Candidate status output is passed through workflow outputs, and recovery does not repeat publication when the pending intent's verified target identity is already live.

Bootstrap operator instructions are in `deploy/README.md`; the scripts/workflow contract notes are in `scripts/README.md`. No new repository environment/protection configuration, secrets, or variables are required. Existing environment configuration is preserved.

## Security incident disclosure and remaining risk

During this task, a read-only SSH Docker diagnostic requested the full production web service environment and emitted its values into agent tool output. The exact diagnostic was the `docker service inspect dofek_web --format '{{json .Spec.TaskTemplate.ContainerSpec.Env}}'` step executed over SSH. No values are repeated in this report, commit, or follow-up. The source-configured credential key names that may be affected include `ACCOUNT_ERASURE_LEDGER_KEYRING_JSON`, `BODYSPEC_CLIENT_SECRET`, `BREVO_API_KEY`, `CONCEPT2_CLIENT_SECRET`, `COROS_CLIENT_SECRET`, `CREDENTIAL_ENCRYPTION_KEY_BASE64`, `DECATHLON_CLIENT_SECRET`, `FATSECRET_CONSUMER_SECRET`, `FITBIT_CLIENT_SECRET`, `GARMIN_CLIENT_SECRET`, `GARMIN_WEBHOOK_SECRET`, `GOOGLE_CLIENT_SECRET`, `KOMOOT_CLIENT_SECRET`, `MAPMYFITNESS_CLIENT_SECRET`, `MCP_OIDC_COOKIE_KEY`, `OPENAI_APPS_CHALLENGE_TOKEN`, `OURA_CLIENT_SECRET`, `POLAR_CLIENT_SECRET`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `STRAVA_CLIENT_SECRET`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `SUUNTO_CLIENT_SECRET`, `SUUNTO_SUBSCRIPTION_KEY`, `ULTRAHUMAN_API_TOKEN`, `WAHOO_CLIENT_SECRET`, `WGER_CLIENT_SECRET`, `WITHINGS_CLIENT_SECRET`, `XERT_CLIENT_SECRET`, `ZIVA_CLIENT_SECRET`, and `ZOHO_DESK_REFRESH_TOKEN`. Treat values emitted by that diagnostic as compromised pending normal owner-led rotation. No rotation was performed because it is outside this implementation authorization. Useful next time: keep controlled command fixtures beside the workflow and capture their failure artifacts under `/tmp/opencode/independent-gates-task-4-*`.
