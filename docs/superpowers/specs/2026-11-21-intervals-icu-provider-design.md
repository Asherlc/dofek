# Intervals.icu provider design

## Goal

One Intervals.icu connection in Dofek Data Sources syncs the connected athlete’s completed workouts, wellness observations, and scheduled workouts. Dofek shows the data on web and iOS. Intervals.icu owns the workout schedule and structured targets. The connection requests read access to the athlete’s data.

## Approach

Use OAuth from the first release. The user chose this approach for the full integration on November 21, 2026. OAuth grants Dofek only the requested data access and supports revocation. A personal API key could start single-account testing before app approval, but would require users to share a credential with broader access. Intervals.icu asks apps intended for multiple users to use OAuth. [API access guide](https://forum.intervals.icu/t/api-access-to-intervals-icu/609/1)

Reuse Dofek’s provider catalog entry `intervals.icu`, connection UI, encrypted token storage, sync queues, processing status, and manual and scheduled sync behavior. Keep the calendar model provider-agnostic. Use existing domain storage and projections for observations the application already supports. [Dofek provider guide](../../adding-a-provider.md) · [Storage and ingestion policy](../../schema.md#storage-and-ingestion-policy)

## Connect and disconnect

- Request `ACTIVITY:READ`, `WELLNESS:READ`, and `CALENDAR:READ` with the shared OAuth state, callback, and S256 PKCE flow. Use comma-separated scopes and a provider-specific form-encoded code exchange. Validate the returned athlete ID and granted scopes before making the connection active. If any requested scope was declined, identify the missing access and let the user reconnect. Store the bearer token and athlete ID per Dofek user. Use the authenticated athlete endpoint alias where supported. [Intervals.icu OAuth guide](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759)
- Use the shared same-account replacement path on reconnect. A failed attempt preserves the existing local connection. Use Intervals.icu’s `DELETE /api/v1/disconnect-app` for explicit disconnect and account erasure through the existing lifecycle hooks. Confirm terminal revocation responses before allowing them to finish an erasure retry. [Intervals.icu revocation contract](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759)
- Disconnect keeps imported data, so retain a protected athlete binding while that data remains. Require the same athlete for a subsequent connection. To switch athletes, use the existing provider data deletion flow and wait for deletion to complete before connecting the new athlete. Include the binding and the new workout records in provider data deletion and account erasure. This keeps activity absence checks, dated wellness records, and calendar reconciliation scoped to the athlete who supplied the stored data. [Dofek disconnect and deletion flows](../../../packages/server/src/routers/provider-detail.ts)
- Register the Dofek OAuth client and redirect URIs with Intervals.icu. Store app credentials in Infisical for each applicable environment, following the existing connection configuration rules. App approval gates live OAuth acceptance and rollout. The published API contract was reviewed on November 21, 2026. Authenticated behavior still needs verification with an approved client and a consenting test athlete. [App registration](https://forum.intervals.icu/t/intervals-icu-oauth-support/2759)

## Completed workouts and wellness

- Use the standard date-bounded sync and backfill window for both datasets. Parse responses at the network boundary, preserve source IDs and local-date context, and keep replays idempotent. Use the shared rate-limit handling for 429s and preserve independent progress for the three datasets when one endpoint fails. Report affected data and actionable connection or rate-limit errors through the existing sync status. [API request and rate limit guide](https://forum.intervals.icu/t/api-access-to-intervals-icu/609/1)
- Store completed activities by upstream ID with the shared activity writer and send available timestamped heart rate, power, cadence, GPS and other already-supported streams through the existing sensor pipeline. Reconcile missing activities only after a successfully fetched, authoritative list for the exact window. Count an ID returned as a restricted stub or with a failed stream retrieval as present. Keep source attribution so the existing activity reconciliation can handle overlaps with other providers. [Activity API reference](https://intervals.icu/api/v1/docs/swagger-ui/index.html#/Activities/listActivities) · [Dofek reconciliation rules](../../adding-a-provider.md#key-conventions)
- Keep source local dates for wellness. Use existing weight and daily-health paths for supported observations such as weight, resting heart rate, HRV, and steps. When marked as temporary, weight and resting heart rate are settings defaults. Import recorded observations for those fields. Store reported sleep duration as a date-level observation and expose it with its source in both clients. Keep the timing and stages unknown when the source supplies only a total. Validate whether the daily metrics catalog already supports the duration end to end, and extend that path if needed. Explicit null clears the corresponding source observation. An omitted field preserves the stored observation. Dofek’s normal read models choose between overlapping sources. [Wellness API reference](https://intervals.icu/api/v1/docs/swagger-ui/index.html#/Wellness/listWellnessRecords) · [Wellness field definitions](https://forum.intervals.icu/t/server-side-data-model-for-scripts/25781/1)
- Use Strava-synced activity stubs only as evidence of upstream presence. For Garmin data the API supplies, keep device attribution on activities and verify the applicable display treatment for wellness records with unknown original sources. The proposed wellness treatment is an Intervals.icu source label and a view-level Garmin disclosure, following Intervals.icu’s own approach. Confirm that treatment before enabling wellness, and confirm restricted and permitted source behavior during live acceptance. [Strava response behavior](https://forum.intervals.icu/t/intervals-icu-api-integration-cookbook/80090?page=3) · [Garmin availability update](https://forum.intervals.icu/t/api-access-to-intervals-icu/609/816) · [Garmin attribution requirements and wellness guidance](https://forum.intervals.icu/t/intervals-icu-api-terms-and-conditions/114087)

## Planned workouts

- Import dated `WORKOUT` calendar events. Store each event’s upstream ID, source-local schedule, sport, title, notes, and structured workout document when provided. Keep target units as authored, including percentages of a threshold. Parse the supported step and repeat shapes for display and keep the original document as source evidence for shapes the UI cannot render. [Planned workout guide](https://forum.intervals.icu/t/downloading-planned-workouts-from-the-api/93737)
- Use one user-owned PostgreSQL model for scheduled workouts, unique by user, provider, and external event ID. Attach it to existing data erasure and provider source filtering. Refresh the requested history and the next 90 days on normal sync. Use bounded calendar requests and reconcile an exact successfully fetched window. A reschedule updates the same event. A deleted event, or an event removed from the enabled calendars within the queried window, disappears from that window after successful reconciliation. A failed or structurally incomplete response preserves the prior snapshot. [Calendar scope and date semantics](https://forum.intervals.icu/t/api-access-to-intervals-icu/609/4)
- Add an upcoming schedule to the existing web and iOS Activities calendar. Group scheduled sessions by day, label each as planned, and provide a detail disclosure for steps and targets. Keep completed-activity totals based on recorded activity. A planned workout and a completed workout can both appear on the same day. Dofek administers the connection and displays calendar data. Workout editing, device execution, and plan authoring remain in Intervals.icu.

## Implementation order and acceptance

1. Implement OAuth, provider registration, read-only setup, and lifecycle tests. Prove connection state survives repeated connects, incomplete grants, and failed reconnects. Verify that disconnect preserves imported records, that switching athletes requires completed provider data deletion, and that revocation and retries use the shared disconnect and erasure entry points.
2. Implement completed-activity and wellness ingestion. Use API fixtures and real-database coverage for bounded reconciliation, replay, source isolation, null versus omission, interrupted sync, and historical backfill. Verify a supported activity and its streams reach existing views and wellness samples appear with attribution.
3. Implement scheduled workout storage and the matching web and iOS calendar views. Verify local dates across time zones and daylight saving time, structured targets, reschedules, removals, failed fetches, and exclusion from completed-workout totals. Cover account erasure, migrations, and updated schema diagrams.
4. Review the entire change, run required local checks, and verify an authenticated connect, sync, reconnect, and disconnect against Intervals.icu before enabling the provider. Use a consenting account with activity streams, wellness data, and an upcoming structured workout. Document the API behaviors observed, including the source restrictions that can be verified with the account.
