# Ghost Sessions

*Proposed design for approval. Direct GPS and map data are the agreed v1 scope.*

## Product behavior

On web and iOS, outdoor run and ride details automatically show repeat routes and shared stretches of road, trail, or climb. A first visit can still show named stretches and recorded performance. The athlete can open a stretch on the map and see where it starts and ends. For a repeated stretch, the map and comparison focus on the traveled portion shared by the two efforts. A full-route match can highlight the stretch that accounts for the largest time difference when the route and stretch timing support that statement.

Each comparable route or stretch opens with a suggested ghost and a short reason. A verified new best defaults to the previous best. Compare records only among efforts measured over the same physical start and finish. Pairwise overlaps with different boundaries can still show a time difference for the portion they share. Other efforts default to the most recent comparable pass in the history checked. The past-match list shows dates, elapsed times, and links to the original activities. Selecting another pass updates the replay and comparison together. The list can page through eligible history. Each pass through a stretch has its own position in the workout, including multiple passes in one workout. While history is incomplete, qualify the comparison by the coverage checked and reserve unqualified first-visit or personal-best claims for complete eligible history.

Both clients show a synchronized map replay and elapsed time difference. Show pace for runs and power or heart rate where both efforts have sufficient recorded coverage. Preserve recorded pauses in elapsed time and disclose the time basis. Label first recorded visits, partial map coverage, and missing sensor data plainly. First release scope is outdoor routes and after-workout review. Live racing, public leaderboards, and a public segment catalog are outside this release.

## Approaches considered

- **Recorded geometry plus managed map matching (recommended).** Reuse Dofek's full-route matcher, deduplicated GPS, and existing Geoapify integration. Geoapify identifies the roads and paths that fit an observed trace. Dofek finds repeat efforts and measures them from recorded data. This uses an existing API account and adds a new use of it that sends location coordinates. [Geoapify map matching](https://apidocs.geoapify.com/how-to/routing/choose-map-matching-mode) · [Existing Dofek setup](../../../deploy/README.md)
- **Recorded geometry plus a self-hosted map matcher.** An OpenStreetMap-based routing engine such as Valhalla can keep trace processing in Dofek's infrastructure. Building, updating, and operating the routing graph adds deployment and storage work. [Valhalla map matching](https://valhalla.github.io/valhalla/api/map-matching/) · [OpenStreetMap attribution](https://www.openstreetmap.org/copyright)

V1 uses direct GPS and map data. Strava API data and values derived from it are excluded from Ghost Sessions. This includes segment boundaries and map matching inputs. The standard Strava API policy restricts combining its data with other customer data. [Strava API Policy, section 5.4](https://www.strava.com/legal/api_policy#section-5-use-restrictions)

## Matching and measurement

Use the existing canonical activity and GPS serving models and the bounded route-equivalence matcher for complete routes. Extend route geometry coverage to eligible outdoor running modes where needed. Require the same direction and lap count. Allow small differences in where recording starts or ends. Loops with substantially different recording start points qualify for shared-stretch comparisons in v1. For shared stretches, locate continuous, ordered overlap between eligible tracks, and compare the same physical start and end in the same direction. Compare only the overlapping portion when two activities enter or leave a named road at different points. A shared name alone cannot establish a match. An ambiguous parallel path, a reversed traversal, a crossing, or a location gap at a split boundary cannot establish timed equivalence. Match repeated unnamed climbs using recorded elevation and geometry, keeping unsupported elevation unavailable.

Use the managed matcher to propose contiguous named sections of the observed trace. Use confidently matched names where available, preserve gaps, and use a description such as “Unnamed climb” when the recorded trace supports that claim. A map reconstruction cannot establish that an athlete traveled through a gap. Timing comes from the recorded samples at the matched boundaries. Align replay positions by progress through the same geometry so each effort shows when it reached the corresponding place. Record and return pass identity as the canonical activity and the interval in that activity. Deduplicate multiple copies of a recording before identifying personal records or offering past matches. Reuse server-side sensor source and coverage rules for comparisons. [Existing route model and incremental refresh](../../../analytics/README.md) · [Activity source and comparison contracts](../../../packages/server/README.md)

Read only eligible, independently sourced GPS and sensor evidence for this feature. Filter by sample provenance before selecting samples or aggregating them. A canonical activity with duplicate Strava and direct-provider members remains eligible through its independent recording, even when existing activity views prefer the Strava copy. Apply the eligibility filter before the existing provider priority chooses a source for Ghost Sessions. The plan must verify which upstream inputs still expose those alternatives. Apply account ownership and activity visibility to both anchor and candidate data. When comparing gaps or incomplete recordings, omit unsupported metrics while preserving any independently evidenced comparisons.

## Processing and data handling

Run map enrichment and expensive geometry preparation off the activity-detail request path. Use the existing activity refresh lifecycle and bounded worker work. Keep match candidates bounded and spatially relevant, and prepare expensive sensor calculations in the existing ClickHouse analytics pipeline. Serve one shared response contract to the existing web and iOS activity details. A provider outage should leave recorded-route matches available and show a distinct status for name enrichment.

The proposed managed path sends a bounded set of eligible GPS coordinates and the travel mode to Geoapify. It excludes account IDs, recorded timestamps, and sensor metrics. Current Geoapify usage sends a submitted place name. This design introduces a disclosure and an account-level opt-in for automatic map labels on new workouts and older workouts the athlete opens. Withdrawal stops enrichment, removes existing map labels from the feature, and expires stored results. Route and climb matching from recorded data remains available regardless of that choice. Named roads and trails are a release requirement. Qualify road and trail coverage, quota, retention, and attribution under Dofek's Geoapify account before enabling it. Measure name coverage and credit use on public or synthetic traces before deciding batch sizes. Retain only the derived records necessary to serve the feature, following the existing expiry, source removal and account erasure paths. [Current public place lookup](../../../packages/server/README.md#activity-identity-and-filters) · [Geoapify API documentation](https://apidocs.geoapify.com/docs/map-matching/) · [Geoapify data processing agreement](https://www.geoapify.com/data-processing-agreement/)

Leave numeric matching thresholds, batch limits, storage representation, and replay controls to the implementation plan. Establish thresholds with representative traces, including short pieces on long workouts, a loop recorded from different starting points, and closely spaced road and trail geometry. Bound historical work explicitly and make older eligible activities available through the same pipeline.

## Acceptance and task order

1. Confirm the route and sensor provenance, and exercise the named-road and named-trail response contract using public or synthetic traces. Confirm map service handling before using customer GPS.
2. Implement and test server-owned full-route and shared-stretch matching, timed comparisons, defaults and history. Verify true matches, reverse and crossing rejection, parallel paths, repeated passes, GPS gaps, cross-provider duplicates, source deletion, and the two-source activity where only one recording is eligible.
3. Implement and test background map enrichment and first-visit breakdown, including missing names, disconnected sections, failure and retry, and withdrawal of the map-label opt-in.
4. Build the activity detail workflow on web and iOS against the same contract. Verify the suggested ghost, past-pass selection, original-activity links, map replay, unavailable metrics, and meaningful empty and error states on both platforms.
5. Review the complete diff and behavior. Use test-first changes, real ClickHouse tests for database behavior, required lint and typechecks, and web/iOS review fixtures. Verify production dependencies and the bounded historical process before release.
