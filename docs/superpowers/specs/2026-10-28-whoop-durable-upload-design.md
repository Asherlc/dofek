# Durable WHOOP capture and delivery

The operator approved native durable sample storage and iOS-managed background uploads after production evidence showed capture accumulating without publication. This change must preserve raw realtime and IMU samples across process recreation and remove them only after the existing authenticated API confirms publication.

## History and approaches

- [PR 1585](https://github.com/Asherlc/dofek/pull/1585), commit `b21f5e8fc`, intentionally stopped ordinary JavaScript uploads after the app entered the background to avoid cancelled requests. [PR 2026](https://github.com/Asherlc/dofek/pull/2026), `ec6f4ac78`, also deferred connection initialization. Do not restore unbounded background JavaScript timers.
- [PR 3053](https://github.com/Asherlc/dofek/pull/3053), `f3aa6a498`, separated realtime and IMU uploads and retired stale upload lifetimes. Preserve independent progress and stale-completion protection.
- [PR 2676](https://github.com/Asherlc/dofek/pull/2676) implemented account-bound Zepp outboxes on a different platform. Reuse its ownership principle; its JavaScript storage cannot run inside the iOS BLE callback.
- No durable WHOOP queue or background URLSession implementation was found in the current branch's relevant history. Reinstating unrestricted fetch or merely increasing memory limits would retain known cancellation and process-loss defects. The chosen approach is native transactional storage plus Apple's background transfer service.

## Contract

Use the system SQLite library for one canonical on-device queue, separate from protocol parsing and connection management. SQLite provides [transaction atomicity](https://sqlite.org/isolation.html). Incoming native samples are serialized using the existing timestamp and field rules and committed before they are considered queued. Reads and acknowledgments operate on bounded rows, not an entire day's samples in memory. Do not evict unacknowledged samples at the former memory limits.

Queue ownership is a persisted account/server binding and generation. Authenticated JavaScript configures the account, server URL, and session token before starting capture. A restored known binding may collect while credentials are being restored; unbound capture must fail visibly. Keep tokens in memory only; the existing SecureStore remains credential storage, while iOS owns submitted request headers. Reconfiguring to another account and explicit sign-out/erasure cancel captured retired transfer identities and purge the former account's queue and transport files. A stale completion cannot acknowledge or restart work for a new owner. An ordinary disconnect/reconnect or app suspension preserves the queue. Existing erasure cutoffs also apply to durable rows and transport files and survive account reconfiguration.

Each stream has one in-flight batch, with at most 500 samples from one peripheral. Persist the batch identity and its selected row IDs, and write an atomic file containing the existing tRPC input. The file is a disposable transport projection over queued samples. Native URLSession background tasks use the existing mutation routes and bearer authentication. Accept only a successful HTTP response with a valid tRPC result containing a nonnegative integer `inserted`; error bodies and malformed responses retain rows. Existing server-side deterministic event identities make replay safe ([realtime writer](../../../packages/server/src/repositories/whoop-ble-sync-repository.ts), [IMU writer](../../../packages/server/src/repositories/inertial-measurement-unit-sync-repository.ts)).

Restore the same session identifier and reconcile OS tasks with persisted batch identities before creating replacement tasks. Rebuild missing transport files from the reserved rows. Register the Expo app-delegate subscriber for background-session completion, finish native callbacks on the main thread, and process acknowledgments without needing React to mount. Apple's [background transfers](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background) require file-backed uploads and delegate-based completion; they provide eventual scheduling, not an immediate-delivery guarantee.

Schedule bounded native work from actual BLE arrivals and authenticated configuration/foreground/background-refresh triggers. Coalesce normal capture into batches rather than creating a task for each notification. On transient delivery failure retain data and retry on a subsequent capture or lifecycle trigger; do not loop tightly on invalid credentials or rejected data. Storage and unexpected transfer failures reach native Sentry and observable diagnostics. No new secrets or server environment variables are required.

Replace the WHOOP JavaScript upload path with native ownership; do not keep two competing consumers of the same queue. Preserve existing connection/reconnect behavior and diagnostics. Native-only behavior has no web equivalent; both clients continue to consume the unchanged server API. Existing alerts remain truthful about connection state; this work does not claim to reconstruct missing historical samples or guarantee an alert for every OS termination.

## Verification

Test persistence by closing and reopening real SQLite storage, exact acknowledgment identities, mixed devices, both streams, failures before acknowledgment, batch-file recovery, concurrent appends, account changes, and erasure. Test native transfer scheduling/response handling with controlled transport boundaries. Test bridge configuration and auth cleanup in the mobile tier. Run the native suites, mobile tests/typecheck, owned-file lint, standalone Swift export checks, and a signed iOS build. A physical iPhone/WHOOP overnight check is necessary before claiming real-world background reliability; [Simulator lacks Bluetooth hardware](https://docs.expo.dev/workflow/ios-simulator/#limitations).
