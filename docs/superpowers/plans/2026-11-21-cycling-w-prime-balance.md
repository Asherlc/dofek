# Cycling W′ Balance Implementation Plan

**Goal.** Estimate the reserve for hard efforts during a completed cycling ride using imported power and a documented same-modality critical power and W′ test in the selected dates.

**Design.** Use the [approved Canvas artboards](../../../design/cycling-w-prime-balance/design.json) as the reference for rider-facing labels and results. The read-only `get_cycling_training_metrics` endpoint is the proposed integration point. Compute on the server and return labeled values with their source evidence. The original scope uses existing imports and adds no data-entry workflow or application UI.

**Implementation prerequisite.** Establish one current import path that supplies a complete, identifiable maximal test protocol and measured power. Keep the implementation paused until this prerequisite is demonstrated or the user approves a different eligibility rule.

## Input evidence

The [activity power curve](../../../analytics/models/read_models/activity_power_curve.sql) already serves measured durations and their acquisition evidence. The durations describe the best recorded power windows. A peak does not establish that the rider undertook a maximal trial or followed a test recovery schedule. The [existing critical-power helper](../../../packages/cycling-power/src/critical-power.ts) fits a work-versus-time regression. Reuse the [regression primitive](../../../packages/cycling-power/src/regression.ts) for a test that specifies inverse-time regression.

For power provenance, trust direct measurement recorded on the selected sample or an explicit provider flag tied to the same source activity. Strava retains `device_watts`, which distinguishes power-meter watts from an estimate. A flag on another member of the deduplicated ride cannot establish the selected stream's origin. [Strava API reference](https://developers.strava.com/docs/reference/)

The [FIT importer](../../../src/fit/README.md) archives original files. The [native decoder](../../../native/fit-decoder/README.md) streams record, device, and weight messages and does not deliver recorded laps or workout steps to the importer. The [interval table](../../../src/db/schema/activity.ts) can hold boundaries and targets, but the current production writer is for Hang Ten, and interval boundaries alone cannot establish a maximal cycling protocol. FIT can associate completed laps with planned workout steps. `active` workout intensity is a category for an interval and cannot establish maximal intent on its own. [Garmin FIT Activity files](https://developer.garmin.com/fit/file-types/activity/) · [Garmin FIT Workout files](https://developer.garmin.com/fit/file-types/workout/)

## Acceptance criteria and task order

For each behavior change, write the regression test first and record the failing and passing runs. Keep the existing activity contracts compatible and review each completed step against the qualifying source evidence.

1. **Prove the import and fit.** Verify an actual source record or redistribution-cleared source fixture with an explicit test identity, completed effort boundaries, compatible recovery, exact modality, and timed measured power. Match the full protocol to a published method. An example indoor candidate is the inverse-time fit from the 12-, 7-, and 3-minute maximal trials interspersed with 60 minutes of passive recovery. Store fixture provenance and test the import-to-fit path with the real query engines. Require finite positive coefficients and retain the unrounded coefficients for the model. Include regression cases for missing test identity, incomplete or inferred intervals, unknown power source, excluded dates, and mismatched modality. [Karsten et al., indoor time-trial reliability study](https://doi.org/10.1371/journal.pone.0189776)
2. **Implement and verify the published balance calculation.** Use Skiba's 2015 differential model, starting with the fitted W′ and consuming complete one-second elapsed power values as in the published calculation. Above critical power, subtract the excess work. Below it, apply the exponential recovery term with time constant W′ divided by the difference between critical and recovery power. At critical power, hold the current balance. Verify the Canvas example gives approximately 12.2, 6.8, 3.2, and 0.6 kJ at the four effort ends, preserve recorded zero watts, and keep signed outputs visible. Unknown power history makes the dependent balance unavailable. Test these cases in the shared cycling-power package. Short-recovery validation found material model error, and recovery constants can transfer poorly across formats. [Welburn et al.](https://doi.org/10.1007/s00421-025-05912-0) · [Balci et al.](https://www.jsc-journal.com/index.php/JSC/article/view/1163)
3. **Expose the result in the existing cycling tool.** Use its bounded exact-range, per-ride request and deduplicated activity samples. Return the method, modality, fit evidence, estimated reserve, and unavailable reason where applicable. Reuse existing recorded interval detail for effort summaries where present. Preserve existing caller behavior and distinguish model estimates from physiological measurements or exhaustion predictions. Run tool and repository tests, relevant unit and real-engine integration suites, repository lint, and workspace typechecks. Review the actual diff and evidence before pushing.

## Direction needed

The normalized inputs checked so far establish timed power but lack one documented test protocol. A focused FIT investigation could examine a real retained file for explicit protocol and completed-lap evidence before changing ingestion. Ordinary outdoor ride bests are another possible input, subject to explicit approval as an exploratory estimate. Karsten's five-week road study used 3-, 7-, and 12-minute best powers and included planned maximal trials. It reported stronger agreement for critical power than for W′. [Karsten et al., field validation](https://doi.org/10.1007/s00421-014-3001-z)
