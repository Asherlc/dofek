# Health Data

Read [README.md](README.md) first for architecture, commands, and deployment runbooks. `AGENTS.md` is the canonical agent guidance; `CLAUDE.md` and `GEMINI.md` are same-directory symlinks.

## General

- **Minimum sound change**: Meet the complete current requirement with the least maintained custom code and machinery. Prefer stock platforms, established tools, and existing workflows; research current authoritative guidance and off-the-shelf alternatives before DIY. Evaluate maintenance, adoption, security, licensing, and operational trade-offs ([OpenSSF Scorecard](https://scorecard.dev/) can inform security review). Use the smallest domain abstraction actual callers need, consolidate duplicate tools, and follow YAGNI. Do not add unrelated error handling, validation, infrastructure, or speculative future-proofing. Preserve correctness, safety, operability, and maintainability rather than minimizing lines; use [Google's review dimensions](https://google.github.io/eng-practices/review/reviewer/looking-for.html).
- **Confirm direction**: Before a non-trivial implementation, strategy, workaround, or choice with meaningful trade-offs, confirm the approach with the user. Ask before departing from YAGNI, cutting corners, or pursuing a hacky fix.
- **No branch switching without approval**: Never switch branches, create a branch from another branch, or rebase onto another branch without explicit user approval.
- **Persist; ask before pivoting**: Exhaust reasonable options for the chosen strategy. Before changing it, state the current strategy, attempted steps and evidence, why it is blocked, and one alternative; ask for approval in one sentence. Do not execute alternative commands or edits before approval.
- **Durable steady state**: Merged production code, configuration, scripts, and workflows must describe the intended steady state. Keep one-time diagnosis/remediation as operator actions. Do not retain incident-specific branches, forced optimizer settings, oversized temporary timeouts, diagnostic-only instrumentation, cleanup hooks, temporary flags, manual-removal TODOs, or commented-out dead code/config. Retain generally useful observability, regression tests, reproducible migrations, and incident documentation.
- **Missing providers**: “I can't see a provider” means its validation is failing. Use the `fix-provider` skill to diagnose missing configuration or credentials; intentionally disabled providers remain hidden.
- **Latest stable versions**: Verify the current latest stable release when adding or updating dependencies, images, services, artifacts, or tools. Pin specific production versions rather than `latest`.
- **Repository scripts**: Use TypeScript (`.ts`) with `pnpm tsx`; Python tooling belongs only inside `packages/ml`.
- **Package manager**: Always use pnpm, never npm or yarn.

## Agent Documentation

- **Local guidance**: Packages and logical directories need their own `AGENTS.md` and `README.md`. Every `AGENTS.md` must instruct agents to read its sibling README first, and have same-directory `CLAUDE.md` and `GEMINI.md` symlinks to it.
- **Audience**: Keep agent-only instructions here; put shared architecture, commands, and runbooks in README or `docs/`. Human documentation must stand alone without skills or an agent present. Update it with significant changes and external API, format, authentication, or provider findings.
- **Sources**: Cite official documentation, specifications, or primary sources for claims added or updated in `AGENTS.md`, `README.md`, and `docs/`; do not assert third-party behavior without evidence.
- **Portable skills**: Keep repository skills in `.agents/skills/<name>/SKILL.md` using the [Agent Skills specification](https://agentskills.io/specification). Keep `.claude/skills` as a relative link to that directory. Use explicit request inputs and command instructions instead of harness-specific substitutions. See [shared skill discovery and layout](docs/development-environment.md#shared-agent-skills) before adding skills or aliases.
- **Written plans**: Execute written multi-step plans with `superpowers:subagent-driven-development` or `superpowers:executing-plans`, keeping review checkpoints explicit in working notes.

## End-of-Task Retrospective

- Close each task with a short account of what worked, what needed investigation, useful context for next time, and missing or unclear guidance. Propose concrete wording/runbook improvements and relevant existing or missing skills for user approval.
- After production incidents, deploy failures, infrastructure/database pressure, CI/deploy outages, or operational debugging, append the date, symptoms, user impact, evidence, root cause (or explicitly unresolved status), fix/mitigation, remaining risk, and follow-up to [the incident baseline](docs/production-incident-baseline.md).

## Debugging

- **Evidence before behavior changes**: Reproduce and diagnose the failure before fixing it. For CI/deploy/infra incidents, capture and cite the exact failing command/step, first fatal log line, and causal explanation. For production debugging, verify working logs/metrics/traces first; repair missing instrumentation before attempting the fix. Confirm hypotheses with evidence rather than “likely” explanations.
- **Root cause before mitigations**: Fix the underlying cause before adding timeouts, retries, sleeps, fallback defaults, compatibility layers, `continue-on-error`, or warn-and-continue behavior. Do not suppress or delay failures as a fix. Justify any resilience tuning that remains after the direct fix. If the cause remains unknown after initial investigation, stop and ask for direction.
- **Fail fast**: Missing required secrets, environment files, configuration, or dependencies must hard-fail immediately with explicit key names. Never silently degrade, swallow errors, or continue with broken state. Ask before disabling checks, adding ignores, taking shortcuts, or introducing temporary migration bridges.
- **Loading performance**: Follow [the loading runbook](docs/performance/loading-performance-runbook.md) first for slow web/mobile loads, blank dashboards, slow tRPC batches, ClickHouse queueing, or query bottlenecks. Classify with Axiom or recorded evidence, preserve stale data during background client refetches, and add ClickHouse/dbt models only when evidence names a request-time query bottleneck.
- **Postgres outages**: Use `.agents/skills/db-incident-response/SKILL.md` first for recovery mode, restart loops, or disk pressure.
- **New environment variables**: Verify each newly referenced variable exists in Infisical for every relevant environment; create missing keys before considering the task done, merging, or deploying.
- **Diagnose operator-workstation Infisical sessions before repeating login instructions**: Record `command -v infisical`, `mise which infisical`, and both versions (Homebrew/mise can differ). Before concluding logout, retry a read-only names-only check with necessary access: `infisical export --env=prod --format=json | jq -r '.[].key'`. Never print raw exports or secret values. This workstation procedure excludes the Cursor VM without Infisical and production, where CI exports secrets. Before `infisical secrets set`, redirect both streams away from tool output, then verify key names; `--silent` alone is insufficient. See [Infisical CLI](https://infisical.com/docs/cli/overview).
- **Incident completion**: Report the root cause in one sentence, its direct fix, successful validation without ad-hoc waits, and a one-line justification for each remaining resilience knob.

## Development Rules

- **Keep list views concise**: State information once. Cards identify the record, key metrics, and status; place supporting detail behind existing disclosures or on detail screens. Show instructions while their action is active; preserve actionable errors and qualifiers. Review visible text and screen-reader labels on web/mobile with browser checks and TDD for interaction changes. Follow the [WAI disclosure pattern](https://www.w3.org/WAI/ARIA/apg/patterns/disclosure/).
- **Server-side metric computation**: Compute every displayed metric on the server. Web/iOS clients render colors, labels, formatting, and layout; they must not derive, aggregate, score, or transform raw metric data. Return all required values in the API response.
- **Good architecture and modeling**: Model real domain concepts with focused types/interfaces, decouple shared logic, and extract scattered checks representing one concept. Apply SOLID: single responsibility, composition-based extension, substitutable implementations, small interfaces, and dependency inversion. Prefer composition, dependency injection, strategies, and mixins over inheritance; add abstractions only for actual callers.
- **Dual-platform parity (web + mobile)**: Implement each feature, bug fix, page, chart, and UI change in both `packages/web` and `packages/mobile` in the same PR; check parity in review. Reuse the domain packages listed in [README.md](README.md) for shared logic. Keep native integrations and rendering libraries platform-specific.
- **Mobile Expo Router route hygiene**: `packages/mobile/app/` contains only routes/layouts/special Router files. Put route tests in `app-tests/`, stories in `app-stories/`, and fixtures in `app-fixtures/`; move helpers out rather than hiding them with `href: null`. [Expo Router treats files under app as routes](https://docs.expo.dev/router/basics/core-concepts/#6-non-navigation-components-live-outside-the-srcapp-directory).
- **Always report errors to Sentry**: Every catch handling an unexpected error must call `captureException()` (`./telemetry` on mobile or the server equivalent). Do not silently catch or only log unexpected failures.
- **Surface errors to the user by default**: Return specific, actionable server error messages with an appropriate `TRPCError` code. Clients display `error.message` rather than hardcoded generic failures.
- **Tie remedies to observed state**: Recommend corrective actions only when the observed state supports them. When the cause is unknown, offer checks without claiming a diagnosis or promising recovery. For example, a generic Bluetooth disconnect does not justify an "Open Dofek" instruction; confirmed app closure can. See the [collection notification policy](packages/mobile/modules/background-refresh/README.md#data-collection-notifications).
- **Never bump size limits**: Fix `size-limit` failures by reducing actual bundle size through deduplication, shared components, lazy loading, or tree shaking. Never raise `.size-limit.json` thresholds.
- **TDD**: Write a failing test before implementing a feature/provider or fixing a bug. Add tests for changed behavior even when the touched code was previously untested. SQL/query bugs require real-database integration tests.
- **Test database behavior with executable database tests**: Execute SQL/dbt behavior against the real engine with minimal fixtures, including nullability, coercion, `FINAL`, joins, maps/arrays, and incremental output. SQL substring assertions are only for static policy that cannot meaningfully be executed.
- **Do not test the absence of a feature**: On deletion, update/remove tests of the deleted behavior; do not add assertions that code, routes, or fields are gone. Negative assertions for active conditional behavior or a real regression remain valid.
- **Do not test static config files**: Do not add or run dedicated unit tests for declarative JSON, XML, YAML, TOML, manifests, or metadata without meaningful runtime logic. Verify with schema-aware tooling, builds, lint, or diff review.
- **Do not replay heavyweight historical backfills in tests**: Do not require broad integration/mutation coverage for one-off production backfills or historical migration bodies. Create current ClickHouse schema/read models directly, then seed/sync minimal fixtures. Do not invoke a tracked migration runner from tests when it replays expensive history.
- **Production code drives, tests adapt**: Never add production hacks, indirection, lazy connections, test-only environment branches, or runtime flags just for tests. Use test mocks or dependency injection; production refactoring for testability must also improve production design.
- **No exports just for testability**: Every export needs a production consumer. Test internal behavior through the public interface.
- **No test/optional-only branches**: Keep production-required dependencies required in types and constructors; test helpers supply stubs. Do not add unreachable production guards or benign empty-result fallbacks that hide infrastructure failures. Runtime precondition failures must be explicit errors.
- **Shared test utilities**: Share mocks, data, and setup through a local `test-helpers.ts`, never through production exports or another `*.test.ts` file.
- **Colocated unit tests**: Use `<source>.test.ts` next to its source, never `__tests__/`. Integration tests use `*.integration.test.ts` where appropriate. Mobile route tests belong under `packages/mobile/app-tests/` to avoid route discovery.
- **Test files map 1:1 to source files**: Each unit test file tests one source file. Split oversized production responsibilities into focused modules and colocated tests; do not split tests by arbitrary scenarios while retaining a monolith.
- **Test separation**: Unit tests (`*.test.ts`) must not require external services. Integration tests (`*.integration.test.ts`) must not use module-level `vi.mock`. Mock third-party services at the network boundary with [MSW](https://mswjs.io/) `setupServer` from `msw/node`, never injected fetch or `vi.spyOn(globalThis, "fetch")`.
- **Approved PowerSync test exception (2026-11-11)**: Only `src/lib/climbing-board-account.integration.test.ts` may mock the `@powersync/node` database boundary. The [SDK uses its own Undici WebSocket](https://github.com/powersync-ja/powersync-js/blob/main/packages/node/src/sync/stream/NodeRemote.ts), while [MSW intercepts the global WebSocket](https://github.com/mswjs/interceptors/blob/main/src/interceptors/WebSocket/index.ts). Keep REST on MSW and PostgreSQL real; retain separate adapter unit coverage and read-only SDK acceptance. This is the user-approved exception for that suite, not a general relaxation of test separation.
- **Use explicit test tiers**: Use [the testing guide](docs/testing.md#integration-dependencies) for Docker-free unit/mobile versus real-database commands and workspace dependencies. Keep CI unit, mobile, integration-shard, and mutation commands explicit; never silently omit a tier. See [Vitest projects](https://vitest.dev/guide/projects).
- **Keep mutation tests Docker-free**: The Stryker Vitest config must exclude `*.integration.test.ts`. Never broaden mutation collection to integration suites; run integration behavior and mutation quality as separate strict gates. See the [Stryker Vitest runner configuration](https://stryker-mutator.io/docs/stryker-js/vitest-runner/).
- **Use the workspace Compose wrapper**: Use `pnpm compose -- <arguments>` or repository scripts with the same physical-workspace identity. Never use raw `docker compose` in Conductor automation: stale inherited working directories can target another workspace. See [project isolation](https://docs.docker.com/compose/how-tos/project-name/) and [`--project-directory`](https://docs.docker.com/reference/cli/docker/compose/).
- **Archive workspace Docker state**: The Conductor archive hook must remove that workspace's default/E2E containers, networks, and named volumes with `down --remove-orphans --volumes`. Preserve other workspaces, shared images, and build cache. See [Compose down scope](https://docs.docker.com/reference/cli/docker/compose/down/).
- **Standing Docker cleanup approval**: The user authorizes removing stopped containers (including other workspaces), pruning rebuildable build cache, and unused images. On disk exhaustion, start with current-workspace disposable resources and `docker builder prune -af`, then inspected stopped containers/unused images. Recheck state immediately before removal. Never force-remove running containers or delete named database volumes under this approval; `docker volume prune` and `docker system prune --volumes` require additional approval. See [container removal](https://docs.docker.com/reference/cli/docker/container/rm/), [pruning](https://docs.docker.com/engine/manage-resources/pruning/), and [local recovery](docs/testing.md#docker-disk-recovery).
- **Mutation testing (Stryker)**: High coverage is a baseline, but the goal is to kill every mutant. When the `Test / Stryker` job fails, check the logs for surviving mutants even if unit/integration tests pass. Add targeted test cases to cover the exact branch, operator, or boundary that survived.
- **Provider-agnostic**: The schema and sync framework must not be coupled to any specific provider. Providers implement a plugin interface.
- **Food DB must stay provider-agnostic**: `fitness.food_entry` and `fitness.food_entry_nutrient` must store food/nutrition facts and generic provider references only. Never add Slack-specific (or any source-implementation-specific) fields to these core food tables.
- **One canonical nutrient storage path**: Store nutrient rows in `fitness.food_entry_nutrient` with definitions in `fitness.nutrient`; never add wide/per-nutrient or duplicate daily tables. Serve totals through `fitness.v_nutrition_daily` or `fitness.v_nutrition_canonical_nutrient` for query-time source resolution. `fitness.v_nutrition_provider_daily` is raw provenance only. These are projections, not stored sources of truth; see [schema](src/db/schema/nutrition.ts) and [PostgreSQL views](https://www.postgresql.org/docs/current/sql-createview.html).
- **Isolated & modular providers**: Keep each provider self-contained under `src/providers/`, implementing `Provider` from `types.ts`. Keep its types, parsing, API client, and sync logic within its own file; providers must not depend on other providers.
- **Raw data only, no duplicate sources of truth**: Store raw or structural data, never derivable averages, totals, durations, or start/end times. Keep exactly one canonical storage location; no mirror/shadow writes or long-term transitional duplicate tables/columns. Migrations must backfill the new location, update every reader/writer, remove old storage, and delete obsolete schema/types/docs/tests. Read-only compatibility views over canonical storage are allowed.
- **Never use provider-estimated calorie expenditure**: Never ingest, normalize, store, serve, analyze, or display provider/device expenditure estimates: workout calories, active/basal energy, or derived balances. Allow only logged nutrition intake and estimates from observed weight change (adaptive TDEE or implied surplus/deficit). Opaque upstream payloads may retain vendor fields for provenance; application code must not consume them.
- **Do not sync sensor-derived analytics back into Postgres app state**: Keep sensor-derived values in ClickHouse queries/read models. Never populate canonical Postgres app state such as `fitness.user_profile` from `metric_stream`, `analytics.*`, or derived Postgres models. Postgres profile state is raw user-entered/provider-supplied data.
- **Deduplicate at query time, not insert time**: Preserve every raw record and its source attribution during ingestion. Resolve provider overlap/source priority in queries or materialized views, never by filtering, merging, discarding, or summing overlapping sources at insertion.
- **Activity sensor analytics must use deduped ClickHouse data**: Read `analytics.deduped_sensor` or derived ClickHouse models such as `analytics.activity_summary`, never raw `ingest.metric_stream`, including in tests/CI fixes. Apply provider overlap and source-priority rules.
- **ClickHouse read models are dbt-owned incremental models**: Put expensive analytics in incremental `.sql` dbt models under `analytics/models/`. Never embed transformation SQL in TypeScript, add naive materialized views that recompute on read, full-refresh in serving/deploy, or refresh history from web/worker requests. Keep `pnpm lint:analytics-policy` enforced. Full refresh/backfill needs explicit operator intent, bounded resources, and a runbook.
- **Name analytics serving tables by domain and grain**: Name new ClickHouse/dbt tables for domain and row grain (`daily_recovery`, `daily_strain`, `daily_sleep`). Avoid architectural suffixes `_read_model`, `_summary`, `_aggregate`, `_table`, and `_model`.
- **Expensive sensor calculations belong in ClickHouse read models**: Compute costly sensor/location operations (centroids, distance, elevation, per-activity aggregates, time-series summaries) in ClickHouse dbt/read models over deduped data, not per request in TypeScript. Preserve canonical provider-agnostic raw inputs.
- **No empty strings as absent values**: Use `null`/`undefined` for absence in storage and application code, never empty-string defaults. Empty strings remain valid for genuine protocol, concatenation, or form-input meaning.
- **No `any` types**: Use proper types, generics, interfaces, or `unknown`; never TypeScript `any`.
- **Minimize `as` type assertions**: Prefer narrowing, guards, discriminated unions, generics, or `satisfies`. Document unavoidable specific assertions in review; never use `as any`, `as never`, or double casts such as `as unknown as X` (enforced by `plugins/no-double-cast.grit`).
- **Zod for runtime data boundaries**: Parse data TypeScript cannot guarantee with Zod: external API responses, SQL results, uploads, webhooks, postMessage/BroadcastChannel, and other runtime boundaries. Prefer `executeWithSchema()` from `packages/server/src/lib/typed-sql.ts` over `db.execute<T>()`; generics do not validate runtime shapes.
- **Avoid acronyms and single-letter variables**: Use descriptive names for variables, parameters, types, and interfaces; spell out domain acronyms. Common unit abbreviations are fine; `_` is the only single-letter exception for unused bindings. See `plugins/no-single-letter-variables.grit`.
- **Layman-readable UI text**: Make titles, axes, legends, tooltips, badges, empty states, and captions understandable without domain expertise. Spell out domain acronyms or put them after a readable name in parentheses. Unit abbreviations such as W, bpm, ms, and km are fine.
- **Storybook stories for every component**: Add/update colocated `.stories.tsx` files for components in `packages/web/src/components/` and `packages/mobile/components/` in the same PR. Cover default, loading, empty, and significant visual variants. Context providers and non-visual utilities are exempt.
- **Avoid generic `View` component names**: Use a domain-specific component name (`Content`, `Panel`, `Body`, `Card`, or its concrete concept), never a generic `View` suffix.
- **No coverage exclusions for convenience**: Improve coverage with tests; never exclude source merely to preserve thresholds. Exclusions are limited to test files, test helpers, fixtures, and `node_modules/`, subject to the standing transitional-code testing preference.
- **No barrel files**: Do not create `index.ts` re-export barrels when splitting modules. Update consumers to import the specific submodule directly.
- **Max 1000 lines per file**: No TypeScript file may exceed 1000 lines; split focused modules proactively.
- **Commit regularly**: Commit at regular intervals — after each meaningful chunk of work (new feature, passing tests, refactor). Don't let changes accumulate.
- **Always push after commit**: Push to remote after every commit so CI runs and changes are backed up.
- **Pre-push checks**: Before every push, run `pnpm lint`, relevant local unit tests (`pnpm test:unit`, `pnpm test:mobile` when mobile code changed, or explicit `*.test.ts[x]` files for the changed units), and typecheck all packages (`pnpm tsc --noEmit`, `cd packages/server && pnpm tsc --noEmit`, `cd packages/web && pnpm tsc --noEmit`). Do not run local E2E/Cypress suites unless the PR adds or changes E2E tests; CI runs E2E coverage. Never push code that fails lint, relevant unit tests, or type checking.
- **Test Docker changes locally end-to-end**: Before pushing Dockerfile/entrypoint edits, build and run the server container against a real database; verify startup, migrations, API responses, and SPA serving. Use [the canonical workspace Compose setup](docs/development-environment.md#commands), not a separate ad-hoc network, fixed sleeps, or an outdated image recipe.
- **Run migrations**: After generating a migration from schema changes, always run `pnpm migrate` yourself — don't tell the user to do it.
- **Never modify repo settings**: Never change GitHub branch protection, required checks, rulesets, or other repository settings through API/CLI. Ask how to proceed if protection blocks merging.
- **Validate infrastructure changes locally before PRs**: For deployment/infrastructure edits (`deploy/*.tf`, server cloud-init, stack, collector config), run `terraform plan` and `terraform apply` locally with Infisical secrets, plus `docker stack config -c deploy/stack.yml`. Verify actual operation before push/PR; CI apply is not a substitute.
- **No manual server changes**: Use committed `deploy/stack.yml` or Terraform for server configuration. SSH is read-only diagnosis (logs, container status, state), never direct configuration editing; the durable fix belongs in code/infrastructure. Follow [README deployment procedures](README.md).
- **Drizzle generate is interactive**: `pnpm generate` can prompt about renames. When unattended generation would prompt, write sequential migration SQL manually, then always run `pnpm migrate` yourself.

## Code Review

- **Flag linter-catchable issues**: During code reviews, still flag violations even if they would be caught by a linter. Do not skip issues just because a linter or Biome plugin enforces them — the review should catch everything, not defer to CI.

## CI

- **Swarm deploy release unit**: Normal web releases use one `docker stack deploy` for web and worker with the same image tag; do not split them into separate deploy jobs/workflows.
- **Knip unused code analysis**: Register new package runtime entry points in root `knip.json`. For whole-package false positives, verify its entry point first.
- **Use the `gh` CLI**: Use `gh` for status and job logs, never scrape the UI or curl raw APIs. Follow [CI debugging](docs/ci-debugging.md) to extract fatal errors from truncated logs, including iOS output piped through `tail`.
- **Use the CI fix skill**: Use the repository `gh-fix-ci` skill for failing Actions checks: inspect logs, extract the first fatal error, prove the cause, implement the minimum direct fix, validate locally and rerun, then report evidence.
- **Keep workflow steps as granular as possible for visibility**: Use small, clearly named CI steps (environment export, readiness, migration, deploy) so progress and failures are visible.
- **Periodically check CI runs** to catch failures early. Before starting work, check if CI is green.
- **Never rerun flaky CI as a fix**: Diagnose and fix every failure, including network, installation, and timing flakes. A rerun alone is not a solution.
- **Prefer Terraform-native CI approaches**: Use Terraform providers, `templatefile()`, and CI plan/apply for infrastructure rather than ad-hoc shell or manual curl/sed pipelines.
